# NPC 波形测试从零教程

这份文档从“还没有写波形测试文件”开始，解释我们为什么需要它、它与原来的 main.cpp 有什么关系、每部分代码做什么，以及如何运行和阅读波形。

先不用试图一次看懂整个 C++ 文件。学习目标只有一个：**看懂 NPC 把取指地址送给存储器，存储器在时钟沿后返回指令，NPC 在 WAIT 状态使用这条指令。**

>
> 前面的交流中，我直接改写了你复制来的三个函数，没解释变化，这是我的问题。本文会专门把它们和原 main.cpp 的写法对应起来。当前测试文件不修改原来的 `csrc/main.cpp` 和 `csrc/minirvEMU.cpp`。

## 1. 讲义要我们检查什么？

讲义要求 IFU 支持同步取指，并给了这样的存储器模型：

```verilog
always @(posedge clock) begin
    ifu_rdata <= pmem_read(ifu_raddr);
end
```

抓住两个信号：

- `ifu_raddr`：NPC 发出的**指令地址**，例如 `0x80000000`。
- `ifu_rdata`：存储器返回的**指令内容**，例如一条 32 位机器码。

你现在的 `vsrc/top.v` 在复位以外实现了同样的同步读取。你的 IFU 用 `idle`、`WAIT` 两个状态配合它：

```text
idle 期间：NPC 给出取指地址
      ↓ 上升沿：存储器采样地址，更新数据；IFU 进入 WAIT
WAIT 期间：指令数据有效，NPC 译码并计算
      ↓ 上升沿：执行结果提交，PC 更新；IFU 返回 idle
```

注意：上升沿**前后**是两个不同的时刻。同一个上升沿中，存储器读取的是沿前的地址；沿后我们才能观察到更新后的 `ifu_rdata`。

讲义说 LSU 暂时无需修改，因此这次主要看**取指通道**，不要误以为数据访问也已经改成了同步 SimpleBus。

## 2. 什么是波形？

波形就是信号值随时间的变化记录。例如，下面只是示意：

```text
时间        0    1    2    3    4    5
clk         0    1    0    1    0    1
rst         1    1    1    0    0    0
state       ?   idle idle  WAIT WAIT idle
```

每次 `clk` 从 0 变到 1 是一个**上升沿**。你的同步逻辑在这些上升沿更新。

波形不是靠肉眼观察运行中的 C++ 打印出来的，而是分两步：

```text
Verilator 运行电路并记录信号
            ↓
       top.vcd 文件
            ↓
GTKWave 打开文件，把变化画出来
```

- Verilator：把 Verilog 转为可运行的仿真模型，并执行它。
- `top.vcd`：波形数据文件，不是截图。
- GTKWave：查看 VCD 的工具。

## 3. 为什么还要写一个 C++ 测试文件？

你的 `top.v` 是被测试电路。它有 `clk` 和 `rst` 输入，但不会自己产生时钟；它还通过 DPI-C 请求读写内存。

测试文件就像给电路搭一个实验台：

```text
wave_test/trace_main.cpp：实验台
  ├─ 从 dummy.bin 读取程序，放入模拟内存
  ├─ 提供 pmem_read / pmem_write / npc_ebreak
  ├─ 给 top 的 rst、clk 赋值
  └─ 通知 Verilator 把电路信号写入 top.vcd

vsrc/top.v + NPC 各模块：被测试的电路
```

`DUT` 是 Design Under Test，意思是“被测试的设计”。文件里的 `dut` 对应仿真顶层 `top`，不是另外一颗 CPU。

### 为什么不直接用原 main.cpp？

原 main.cpp 还在做逐周期 difftest：每循环一次就让参考模型运行一条指令。现在 DUT 的取指与执行需要两个周期，原比较节奏没有对齐，可能第一条就报 PC 不一致。

独立波形程序不调用参考模型，因此可以继续跑 DUT 并记录波形。**它不是 difftest 的替代品**：程序运行到 ebreak、a0 为 0 只能给出该测试的基本结果，不能证明每条指令都经过参考模型比较。

### 为什么放在 wave_test 目录？

项目 Makefile 使用 `csrc/*.cpp` 收集源文件。若把另一个带 `main()` 的文件放进 `csrc`，原构建可能遇到两个 main 入口。放在 `wave_test/` 并单独编译，就不影响原来的测试平台。

## 4. 从零写文件：先搭大框架

在讲解中，假设我们新建 `wave_test/trace_main.cpp`。完整文件现在已经存在，本节是解释它的构造顺序，不要求重写。

先引入头文件：

```cpp
#include "Vtop.h"
#include "verilated.h"
#include "verilated_vcd_c.h"
#include <cstdint>
#include <cstdio>
#include <cstdlib>
```

- `Vtop.h`：Verilator 根据顶层 `top` 生成的 C++ 模型接口。
- `verilated.h`：Verilator 运行时接口。
- `verilated_vcd_c.h`：VCD 波形记录器接口。
- `cstdint`：提供 `uint8_t`、`uint32_t`、`uint64_t` 等整数类型。
- `cstdio`：文件操作与打印，如 `std::fopen`、`std::printf`。
- `cstdlib`：这里用于 `std::rand`。

然后构造主函数的大顺序：

```cpp
int main(int argc, char **argv) {
    // 1. 加载 bin 到模拟内存
    // 2. 开启波形追踪，创建 dut 和记录器
    // 3. 产生复位时钟，并记录
    // 4. 循环产生运行时钟，并记录
    // 5. 检查结束情况，关闭波形文件
}
```

`argc`、`argv` 是命令行参数：程序可以选择默认 dummy，也可以从命令行接受另一个 bin 的路径。

## 5. 先搭模拟内存：mem、地址和数组下标

测试文件里定义了：

```cpp
static constexpr uint32_t MEM_BASE = 0x80000000u;
static constexpr uint32_t MEM_SIZE = 128u << 20;
static uint8_t mem[MEM_SIZE];
```

这和你原来写的三行功能相同：

```cpp
static uint8_t mem[128 << 20];
static uint32_t mem_base = 0x80000000u;
static uint32_t mem_size = sizeof(mem);
```

只是常量改成了大写名字并使用 `constexpr`：表示这些值固定不变。`128u << 20` 是 128 MiB，`uint8_t` 每个元素是一字节。

地址关系：

```text
NPC 地址             C++ 数组
0x80000000      →    mem[0]
0x80000001      →    mem[1]
0x80000004      →    mem[4]
```

也就是说，要先用 NPC 地址减去 `MEM_BASE`，才能得到数组下标。

## 6. 把真实测试程序加载进内存

光定义 `mem` 不够，静态数组启动时是零；要把磁盘里的 bin 读进去。当前文件里的 `load_bin(path)` 与你原先参照 main.cpp 写的思路一致：

```text
fopen(path, "rb")     以二进制方式打开文件
fseek / ftell         计算文件大小
检查大小               防止超出 mem
fread                  读入 mem
fclose                 关闭文件
```

最关键的是：

```cpp
std::fread(mem, 1, size, fp);
```

这表示从文件读取字节，放入 `mem` 开头。原先写 `fread`，现在写 `std::fread`，都是使用 C++ 标准库的文件读取功能。

主函数先选择文件，再调用 `load_bin`：

```cpp
const char *bin = argc > 1 ? argv[1] : "默认 dummy 的路径";
if (!load_bin(bin)) return 1;
```

`argc > 1` 表示命令行提供了文件路径；否则使用默认路径。加载失败就退出，不让 NPC 去执行空内存。

## 7. 三个 DPI-C 函数：为什么需要、与原代码怎么对应

`top.v` 写着 `import "DPI-C" ...`，表示 Verilog 需要调用外部 C 接口。测试文件必须提供这三个函数，否则链接仿真程序时找不到它们。

```text
top.v 发出请求                 C++ 测试平台提供
pmem_read(addr)      ─────→   读模拟内存或 MMIO
pmem_write(...)      ─────→   写模拟内存或 UART
npc_ebreak(pc)       ─────→   记录测试程序结束
```

### 7.1 pmem_read：读数据

函数入口：

```cpp
extern "C" int pmem_read(int addr) {
    const uint32_t a = static_cast<uint32_t>(addr);
    // 根据 a 选择 UART、计时器或普通内存
}
```

`extern "C"` 让函数以 DPI-C 需要的 C 链接方式暴露。

`int addr` 是 DPI 接口传来的 32 位地址；`a` 把同样的位模式当成无符号地址。比如 `0x80000000` 最高位为 1，转成 `uint32_t` 后更容易按地址范围理解。原写法 `(uint32_t)addr` 与 `static_cast<uint32_t>(addr)` 在这里目的相同；后者只是 C++ 的显式转换写法。

普通内存中：

```cpp
const uint32_t off = (a - MEM_BASE) & ~3u;
```

先减去基址，再把低两位清零，得到对应的四字节对齐下标。这与原代码的 `raddr & ~3u` 是同样思路。

再把四个字节拼成一个 32 位值：

```cpp
uint32_t data = uint32_t(mem[off]) |
                (uint32_t(mem[off + 1]) << 8) |
                (uint32_t(mem[off + 2]) << 16) |
                (uint32_t(mem[off + 3]) << 24);
```

最低地址字节放在低 8 位，这是小端序。每个字节先转成无符号 32 位再左移，让表达式的位运算更明确；它与原函数想实现的拼接功能相同。

UART 状态 `0x10000004` 和计时器 `0x20000000/04` 是特殊地址，不按普通 `mem` 处理。当前波形平台保留了随机 UART 状态和基于 `sim_cycle` 的计时思路。它没有接参考模型，不需要原 main.cpp 和 minirvEMU 之间共享的 `uart_status`、`hi`、`lo` 变量：这里直接返回相应值。它是独立仿真模型，不应假定与参考模型共享 MMIO 状态。

**一拍延迟不是 pmem_read 函数自身造成的**。它只是根据地址返回值；同步取指延迟来自 top.v 的 `always @(posedge clk)` 对 `ifu_rdata` 的更新。

### 7.2 pmem_write：写数据

与原函数相同的思路：

1. 把地址、数据、掩码按无符号位模式理解。
2. UART 地址 `0x10000000`：输出一个字节。
3. 内存地址范围外：不写普通内存。
4. 范围内：地址对齐，根据掩码逐字节写入。

```cpp
if (mask & (1u << i)) {
    mem[off + i] = static_cast<uint8_t>(value >> (8 * i));
}
```

`mask` 的第 `i` 位为 1，就写第 `i` 个字节。原代码用 `& 0xff` 取低字节；这里转换成 `uint8_t` 也会保留低 8 位。当前文件改变了写法，不是改变成另一套总线协议。

### 7.3 npc_ebreak：通知程序结束

```cpp
static bool is_ebreak = false;
static uint32_t ebreak_pc = 0;

extern "C" void npc_ebreak(int pc) {
    is_ebreak = true;
    ebreak_pc = static_cast<uint32_t>(pc);
}
```

起初标志为 false。NPC 执行 ebreak 时，top.v 调用这个函数，标志变成 true 并保存 PC。它相当于你原来的 `is_ebreak` 和 `dbgpc`，只是 `dbgpc` 改名为 `ebreak_pc`。

## 8. 波形记录语句逐句解释

先看整体：

```cpp
Verilated::traceEverOn(true);
Vtop dut;
VerilatedVcdC trace;
dut.trace(&trace, 99);
trace.open("top.vcd");
uint64_t t = 0;
```

- `traceEverOn(true)`：在第一次 eval 前告诉 Verilator 本次需要追踪。
- `Vtop dut`：创建电路模型。
- `VerilatedVcdC trace`：创建 VCD 记录器。
- `dut.trace(&trace, 99)`：让记录器追踪 dut 的信号。`99` 是层级深度，不是周期数。
- `trace.open("top.vcd")`：打开输出文件。相对路径对应**运行仿真命令时的当前目录**。
- `uint64_t t = 0`：定义波形时间标签。

每当输入改变，需要：

```cpp
dut.clk = 1;       // 改变时钟输入
dut.eval();        // 让电路计算这个变化
trace.dump(t++);   // 把计算后的信号写到 VCD，并让时间标签加一
```

顺序是**设置输入 → eval → dump**。`t++` 先使用当前值，再加一，因此记录的时间按 0、1、2……递增。

这里的 `t` 是 VCD 的时间标签；它不自动推进 Verilator 的上下文时间。当前测试没有依赖 Verilog 延时调度；以后若使用 `#delay` 等时间特性，需要改用相应的上下文时间和调度方法。

## 9. 复位和运行循环怎么读？

复位部分：

```cpp
dut.rst = 1;
dut.clk = 0; dut.eval(); trace.dump(t++);
dut.clk = 1; dut.eval(); trace.dump(t++); // 上升沿，执行同步复位
dut.clk = 0; dut.eval(); trace.dump(t++);
dut.rst = 0;
```

`dut.clk = 0; dut.eval(); trace.dump(t++);` 写在一行只是为了简短，仍然是三条独立语句。你的 IFU 是同步复位，所以 `rst=1` 时要经过一个上升沿。

接着运行：

```cpp
while (!is_ebreak && sim_cycle < max_cycles) {
    dut.clk = 1; dut.eval(); trace.dump(t++);
    dut.clk = 0; dut.eval(); trace.dump(t++);
    ++sim_cycle;
}
```

每轮让时钟 `0 → 1 → 0`，产生一个上升沿。遇到 ebreak 后结束；若没遇到，达到周期上限也会停止，防止无限运行。

结束后测试平台通过 `dbg_raddr = 10` 读取 a0（x10）。对于采用 AM 退出约定的测试，ebreak 时 a0 为 0 表示成功。最后执行 `dut.final()` 和 `trace.close()` 完成收尾。

## 12. GTKWave 里具体点什么？

不同版本的界面按钮名称可能略有差异，但流程相同：

1. 左上角层级树展开 `TOP` / `top`。
2. 选中 `top`，在信号列表找到 `clk`、`rst`、`pc`、`ifu_raddr`、`ifu_rdata`。
3. 选中信号，使用 **Append** 或类似按钮，把它们加到右侧波形区。
4. 展开 `u_npc`，加入 `inst_valid`。
5. 展开 `u_ifu`，加入 `state`。如果某个内部信号在你的编译或 GTKWave 中不可见，先确认展开的层级和 trace 编译选项；不要用猜测代替观察。
6. 点击工具栏的 **Zoom Full**（缩放到全部波形），再放大最左边的复位和前几个周期。
7. 对 `pc`、`ifu_raddr`、`ifu_rdata` 选择十六进制显示（通常在右键信号后的 Data Format / Hex 菜单）。

## 13. 第一条指令应该怎么看？

以 `P0 = 0x80000000` 为例。不要死记具体数据：用波形里的值，对照 bin 或反汇编文件确认该地址对应的机器码。

```text
                复位后 IDLE       第一个上升沿后 WAIT      第二个上升沿后 IDLE
state           idle              WAIT                    idle
inst_valid      0                 1                       0
pc              P0                P0                      P1
ifu_raddr       P0                P0                      P1
ifu_rdata       复位值/NOP        mem[P0] 的指令          仍可能是 mem[P0]
```

逐步看：

1. 复位后 PC 为 `0x80000000`，所以 IFU 给出同样的取指地址。
2. 第一个运行上升沿前，存储器看到地址 P0；沿后 `ifu_rdata` 变成 P0 对应的指令，IFU 进入 WAIT，`inst_valid=1`。
3. 下一个上升沿，当前指令提交，PC 更新为 P1，IFU 回到 IDLE。
4. 此时 `ifu_rdata` 仍可能是 P0 的指令，因为这个上升沿存储器看到的是沿前的 P0；但 `inst_valid=0`，不能把旧数据再执行一次。
5. 再下一个上升沿，存储器采样 P1，进入 WAIT 后看到 P1 的指令。

`P1` 不一定永远是 `P0 + 4`：如果当前指令是跳转，P1 是跳转目标。观察地址与指令是否对应时，也要留意跳转。

可以再加入 `u_npc.wen` 和 `mem_write`：在 IDLE、`inst_valid=0` 时它们应为 0；WAIT 中是否为 1 则由当前指令类型决定。注意波形上的高电平表示使能条件，真正写入发生在对应时钟沿。

## 14. 常见卡点

**编译说找不到 pmem_read / pmem_write / npc_ebreak？**  确认编译命令里包含 `wave_test/trace_main.cpp`，并且这三个函数使用 `extern "C"`。

**提示 Vtop 没有 trace 成员？**  检查 Verilator 编译命令是否包含 `--trace-vcd`，并重新构建。

**找不到 dummy.bin？**  检查默认路径或在命令行明确传入已有 bin 的路径。

**没有看到 top.vcd？**  确认仿真确实运行成功，并检查执行仿真命令时所在的目录；文件使用的是相对路径。

**没有复位？**  波形里确认 `rst=1` 时存在 `clk: 0→1` 上升沿。

**程序达到周期上限？**  这表示未观察到 ebreak，不等于测试成功；检查 bin 路径、波形和 PC。当前平台有周期上限，某些较长程序可能需要调整上限。

**IDLE 时 rdata 是上一条指令，是错的吗？**  不一定。同步读取的输出可能保留旧值；关键是 `inst_valid=0` 时旧指令不能提交。

**只看到了几拍？**  本独立波形程序不会因原 main.cpp 的 difftest 退出，但可能遇到 ebreak 或周期上限。检查终端输出。

## 15. 一句话回顾

`trace_main.cpp` 给 NPC 装程序、产生时钟并保存信号；`top.v` 在时钟沿用 `ifu_raddr` 更新 `ifu_rdata`；GTKWave 把 VCD 画出来，让我们验证 **IDLE 给地址、WAIT 用返回数据、提交后更新 PC**。
